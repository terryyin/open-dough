# Which retrospective findings deserve the next reader's attention?

Doughnut and Pygardon developers write findings, and project and Open Dough maintainers spend time matching, triaging and revisiting them. The two pilots ask different questions of the same execution history. Each can be judged against current practice in both projects.

### Pilot when a repeat adds useful retrospective evidence

**Identity:** SEED-401#pilot-repeat-retrospective-findings

**Goal.** A maintainer triaging Doughnut or Pygardon findings can see when another incident changes priority, the explanation, or the assessment of a correction, without rereading an account of each harmless repeat. The reviewer writing the retrospective spends a full row only on an occurrence that teaches something. Terry gets a keep or revise decision on that recording choice, judged against current practice under [ADR 0010](../../docs/adrs/0010-definition-of-improvement-accepted.md). [Client recording rule](../../Distribution/src/skills/dough-execution-retrospective/references/process-finding-recording.md) · [Existing collection and reconciliation](../../.agents/skills/collect-client-feedback/SKILL.md#collect-reconcile-and-adopt)

**Scope**

- **Trial rule.** One removable trial paragraph in Doughnut's and Pygardon's `AGENTS.md` replaces a single choice in the recording rule: what a new execution writes on a finding it matches. The reviewer asks what this occurrence teaches that could change the next action. A full row records a material new effect, a cost that changes priority, a newly affected workflow, a corrected attribution, or the adopted response succeeding or failing when the entry names one. A repeat that teaches none of these leaves one line with its execution identity, time, tool and Open Dough release. A reviewer who cannot tell writes the full row.
- **Unchanged.** Matching, numbering, one entry per execution, the no-op reread, and a separate identity for a new cause stay with the existing rule. The distributed rule, the collector and the other clients keep current practice and serve as the baseline. The [sibling pilot](#assess-new-retrospective-findings-pilot) owns first reports.
- **Evaluation.** Write the comparison and the keep and revise criteria before any run, using the [shared comparison](#pilot-comparison). Replay the three case groups below once with each wording, each by a fresh reader shown only what was knowable at that execution. Then judge the next five ordinary executions in each project after the trial rule lands, chosen from story, Git or CI history before opening the findings files, including executions that reported nothing. Record the result with the [existing evaluations](../../docs/maintainer/empirical-process-control-research.md).
- **Decision and close.** Keep if fewer repeat narratives reach triage and total effort falls while material changes, frequency and post-response counterexamples stay discoverable. Revise if a compact line hides an escalation, the wrong mechanism is merged or split, or the maintainer has to reconstruct what a row would have said. A sample with no repeat leaves effectiveness open. An unverified execution release leaves the failed-fix judgment open. On keep, queue promotion into the distributed rule; that story removes the trial paragraphs when its release is installed. Otherwise this story removes them.

**Observed on 18 November 2026.** Since 1 October, commits that only added to `DearDough.md` recorded about 215 rows in Doughnut and 472 in Pygardon, with 111 and 186 new headings. Roughly half of the rows therefore went to existing findings, each in the seven-line form. After collection a client entry is a short summary with a count and a link to the shared record, such as “One 0.3.60 execution”: 76 of Doughnut's 92 entries and 145 of Pygardon's 162 hold no row. The reviewer therefore judges “new” against that summary, and the collector, which already connects executions to open response observations by project, execution and release, judges recurrence after a released response from the compact line. These counts are approximate; merge commits and maintenance edits were excluded by diff shape only.

## Compare the pilots with current practice

For each pilot, state the comparison and keep/revise criteria before observing fresh runs. Use the same historical inputs for current and candidate wording, varying only the selected recording decision. Show the reviewer what was knowable at that execution. Reveal later corrections, retirements and rejected remedies only when judging the decisions. Historical replay is exploratory. Record the project, guidance revision and actual route used for each fresh observation. [ADR 0005](../../docs/adrs/0005-cross-tool-validation-accepted.md) · [ADR 0010](../../docs/adrs/0010-definition-of-improvement-accepted.md)

Select a small ordinary-work sample in **each** pilot project from story, Git or CI history before inspecting the findings files. Include executions that produced no report. Check for missed first incidents, accumulating costs and evidence for or against an earlier response. Count decisions changed, consequential misses and duplicate narratives reaching triage. Compare writer and downstream reviewer effort, including checking skipped cases, using available time, tool or token evidence. Keep active time, elapsed time and token counts distinct. Record sample counts, exposure and missing evidence. A shorter file or a higher fraction of graduated findings alone cannot establish a gain. Use existing execution records and each pilot's assessment to avoid maintaining a ledger of rejected observations. [Existing evaluation measures](../../docs/maintainer/empirical-process-control-research.md#a-small-set-of-decision-oriented-measures)
