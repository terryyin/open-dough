# Which retrospective findings deserve the next reader's attention?

Doughnut and Pygardon developers write findings, and project and Open Dough maintainers spend time matching, triaging and revisiting them. The two pilots ask different questions of the same execution history. Each can be judged against current practice in both projects.

<a id="pilot-new-retrospective-findings"></a>

### Pilot which new retrospective findings to record

**Identity:** SEED-401#pilot-new-retrospective-findings
```json dough-story-state
{"schemaVersion":1,"refinement":"not-refined","approach":"unselected"}
```

**Outcome.** A reviewer can recognize a consequential first report, even with an unknown cause or remedy, and can finish an uneventful retrospective without sending routine execution detail to triage. Today the client records supported one-offs, successful practices and potential general issues. Its comparison of impact, recurrence, actionability and evidence quality comes under file-size pressure, at 1,000 lines. Try the admission decision before allocating an ID or collecting row metadata. [Recording rule](../../Distribution/src/skills/dough-execution-retrospective/references/process-finding-recording.md) · [Retention rule](../../Distribution/src/skills/dough-execution-retrospective/references/bounded-process-log.md)

**Trial question.** What future decision could this observation change? Look for a concrete consequence, a credible near miss with an identifiable failure path, a practice someone could use in a different situation, or evidence answering an open question. One serious event can qualify immediately. A control working as expected belongs with its execution proof unless it changes a choice. A supported open question can be valuable before anyone knows how to fix it.

A reviewer proposing its adoption elsewhere should be able to name that new use. If the fresh sample contains no informative opportunity, leave effectiveness open.

### Pilot when a repeat adds useful retrospective evidence

**Identity:** SEED-401#pilot-repeat-retrospective-findings
```json dough-story-state
{"schemaVersion":1,"refinement":"not-refined","approach":"unselected"}
```

**Outcome.** A maintainer can see when another incident changes priority, the explanation, or the assessment of a correction, without rereading an account of each harmless repeat. Today's recording rule requests a row for each new execution. The collector already matches aliases, distinguishes executions and shortens duplicate narrative after collecting it. Test the choice at the time of recording. [Client recording rule](../../Distribution/src/skills/dough-execution-retrospective/references/process-finding-recording.md) · [Existing collection and reconciliation](../../.agents/skills/collect-client-feedback/SKILL.md#collect-reconcile-and-adopt)

**Trial question.** What do we learn from this occurrence that could change the next action? Preserve a material new effect, cumulative cost that changes priority, a newly affected workflow, corrected attribution or an observation of the adopted response succeeding or failing. Where frequency drives the decision, retain a compact, recoverable count of distinct project/executions with representative locators. Make an identical reread a no-op. A new cause can deserve its own identity even when the symptom is familiar.

## Compare the pilots with current practice

For each pilot, state the comparison and keep/revise criteria before observing fresh runs. Use the same historical inputs for current and candidate wording, varying only the selected recording decision. Show the reviewer what was knowable at that execution. Reveal later corrections, retirements and rejected remedies only when judging the decisions. Historical replay is exploratory. Record the project, guidance revision and actual route used for each fresh observation. [ADR 0005](../../docs/adrs/0005-cross-tool-validation-accepted.md) · [ADR 0010](../../docs/adrs/0010-definition-of-improvement-accepted.md)

Select a small ordinary-work sample in **each** pilot project from story, Git or CI history before inspecting the findings files. Include executions that produced no report. Check for missed first incidents, accumulating costs and evidence for or against an earlier response. Count decisions changed, consequential misses and duplicate narratives reaching triage. Compare writer and downstream reviewer effort, including checking skipped cases, using available time, tool or token evidence. Keep active time, elapsed time and token counts distinct. Record sample counts, exposure and missing evidence. A shorter file or a higher fraction of graduated findings alone cannot establish a gain. Use existing execution records and each pilot's assessment to avoid maintaining a ledger of rejected observations.
