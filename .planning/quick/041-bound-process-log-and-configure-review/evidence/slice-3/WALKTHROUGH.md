## Manual priority review

Byte count and git history cannot prove good selection. The ordinary candidate
was 1,010 lines (995 existing + `DD-005` severe finding
[`records/severe-failed-write-retry.md`](records/severe-failed-write-retry.md)).
Compared using supported impact, likely recurrence, current actionability, and
evidence quality — not numeric scores, age, file position, recurrence count
alone, or text length:

| Material | Priority judgment | Action |
| --- | --- | --- |
| Incoming `DD-005` failed-write retry that discarded uncommitted user notes | Severe one-off: data loss, currently actionable, strong evidence | Record |
| `DD-001` extra blank line in generated notes (top of file, frequent cosmetic notes) | Low impact, not currently actionable, weak evidence. Recurrence and top position do not protect it. | Whole-issue removal |
| `DD-002` occurrence `record:slice-3-dd002-c` | Redundant restatement of `dd002-a` with no new locator | Occurrence removal, preferred before dropping the whole issue |
| `DD-002` occurrences `dd002-a` and `dd002-b` | Distinct executions with remaining learning | Retain |
| `DD-003` skipped plan-conflict handoff that rewrote an approved contract | High impact, likely recurrence, currently actionable, decisive evidence | Retain intact; do not strip evidence to meet size |
| `DD-004` extra comma in one model identifier (highest numbered) | One-off formatting, not actionable | Whole-issue removal, including the highest code |

`DD-001` being first in the file was not a reason to keep it. `DD-002`'s extra
row count was not a reason to keep the redundant row over the severe one-off.
Padding length on `DD-001`/`DD-004` was not a priority rule; those notes left
with their low-value issues. The severe finding did not outrank stripping
`DD-003`.

## Behavior review

1. **Invocation context.** Description names the 500-line warning, 1,000-line
   ceiling, and recoverable replacement when a write would overflow. The
   recording section loads the size/write/retention reference only for an enabled
   process write. Skip flags and stored process preference still select reviews
   first.
2. **Required context.** A candidate write needs an interpretable log and a
   complete candidate whose physical line count can be measured. Bounded
   retention also needs verified recovery (including uncommitted bytes when they
   would be removed), interpretable retained identity, and enough lower-priority
   material. Missing or skipped process selection still stops before any log
   or size inspection.
3. **Useful outcome.** 995→1010 overflowed; bounded write recorded the severe
   finding at 58 lines with recovery and high-water. Occurrence removal and
   whole-issue removal, including the top entry, were choices in that same flow.
   Identity continued: no resurrection, honest DD-003 rows, recovered DD-001,
   no reuse of DD-004. Refusals preserved bytes and independent reviews.
