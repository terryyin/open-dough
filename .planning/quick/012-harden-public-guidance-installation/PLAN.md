## Goal and scope

An adopting developer can install the expanded Open Dough public payload without
the installer escaping the selected project or making an avoidable partial
change when destination topology is invalid.

The completed story promises that installation writes only the three declared
public guidance files and the updater's version record under the selected native
skill root, preserves unrelated and other-platform content, stops ordinary
repeat installation before writes, and reports a replacement failure truthfully.
This follow-up hardens those existing promises for symlinks, non-directory
collisions, and real copy-command failures.

Keep the current three-file payload, platform mappings, numeric-release model,
force authorization, and version-record semantics unchanged. Exclude release
publication, rollback or transaction machinery, local-edit merging, guidance
reconciliation, and changes to the ADR-awareness behavior itself.

## Ordered slices

### 1. Refuse unsafe destination topology before any installation write
Type: Behavior
Status: done
Proof: Add a focused installer fixture that exercises each platform with a
symlinked native skill root and with a regular file at each managed skill path.
Snapshot the target and an outside sentinel before invocation; observe a named
unsafe-path or collision error, no outside write, no newly created earlier
managed directory, and unchanged snapshots. Keep the existing successful
three-file install and ordinary-repeat checks green.

Behavior: A selected native skill root resolves outside the target, or either
managed skill path already exists as a non-directory object → run ordinary or
forced installation → refuse before creating or replacing any managed path and
identify the unsafe destination.

Resolve and validate the selected target/root relationship without following a
repository-controlled symlink into another location. Treat every existing
filesystem object at a managed skill path as a collision for ordinary install;
force may replace managed files only after the selected root passes containment
validation. Preserve other-platform and unrelated paths.

### 2. Report a real mid-copy replacement failure without advancing the record
Type: Behavior
Status: done
Proof: Add a deterministic fixture in which the payload copy command succeeds
for an earlier managed file and fails for a later one. Observe a nonzero exit,
the established incomplete-install and explicit-force recovery message, no
success message, and the prior updater `VERSION` byte-identical. Keep the
existing synthetic copy/verify fault and valid force-replacement checks green.

Behavior: A selected, authorized replacement starts and an actual payload copy
fails → stop immediately, retain the last successful version record, and tell
the adopter that installed files may be incomplete and explicit `--force`
reinstallation is the recovery path.

Handle command failures through the same truthful failure boundary as the
existing deterministic fault path. Do not claim rollback or attempt to infer
which partially copied files remain.

## Decisions and evidence

- CI observation for this execution was unavailable because the active `gh`
  credential was invalid and the observer published no terminal result;
  `pendingCi: unobserved` must not be read as a green CI result.
- Canonicalizing the selected project first, then rejecting symlinks and
  non-directory objects along the selected platform root and both managed skill
  paths, provides a complete pre-write boundary for ordinary and forced installs.
- Real payload-copy command failures now share the synthetic failure's single
  incomplete-install boundary, before the successful-version record is written.
- Review reproduced an out-of-target write by making `.agents/skills` a symlink;
  all three payload files and `VERSION` appeared in the outside directory.
- Review reproduced the collision residue by placing a regular file at
  `.agents/skills/dough-adr-awareness`; installation failed from `mkdir` only
  after creating `.agents/skills/dough-update`.
- These are corrections to the completed installation boundary, not new
  installation behavior or guidance-reconciliation scope.
