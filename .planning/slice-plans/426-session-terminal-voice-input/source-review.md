## Launch input

Goal: Use a compact session-bar microphone to turn speech into text and insert it into the open session's current terminal input, so a developer can continue an existing session without a new launch or copying from a dialog.
Scope:
- Add a small microphone icon button to the session bar, immediately before Mark as done when that action is available. Keep it with the other session actions when Mark as done is unavailable. Give the icon an accessible name and keep it usable with touch and keyboard at narrow and desktop widths.
- Let the developer start and stop recording from that control, with clear microphone-permission, recording, and transcription feedback. The microphone starts capture and becomes Stop while recording; a pending permission or transcription request cannot start another capture. Status must be available without relying on color or hover. Keep the header compact and Close reachable; ordinary terminal typing remains available during dictation.
- Offer each successful transcript once to the same terminal's normal input path at its input position when the result arrives, then return focus there. Do not clear, reconstruct, or replace existing native input. The developer edits and submits through the terminal's normal controls. Dictation sends text without Enter or terminal control actions: render transcript line breaks as spaces and remove other terminal control characters so provider text cannot submit input, move the cursor, or issue an escape command. Preserve the spoken words and punctuation. Do not copy the launch field's blank-line separator into terminal input.
- Reuse applicable recording, transcription, configuration, and recovery behavior already provided for launch instructions. Missing setup, microphone permission refusal, unsupported recording, empty speech, and transcription failure leave ordinary terminal typing available and offer understandable guidance or an explicit retry.
- Associate capture and its result with the session where recording began. Closing or switching the session view releases recording and cancels pending work, including a permission request granted after dismissal; a late result must not enter another session or a reopened instance of the old view. Mark as done that closes the view has the same cleanup. If transcription succeeds but the attachment cannot accept text, retain the complete transcript in this session view, explain that it was not inserted, and offer explicit Insert after reconnect plus Discard. Do not replace the retained result with a new recording: settle it through Insert or Discard first. Closing or switching discards it. No automatic replay of input already offered to the connection: the current terminal transport has no delivery receipt, so replay could duplicate text.
- Add focused frontend proof for placement, voice-to-terminal input, and lifecycle/failure behavior, and update maintained session documentation.
Required restrictions and reasons:
- Dictation cannot send Enter or terminal control characters because the developer must retain the promised opportunity to edit before submission.
- A result cannot outlive its session view or move to another session because it could otherwise enter instructions into the wrong native conversation.
- Do not replay an uncertain send automatically; without a delivery receipt, that could duplicate an instruction. Once is one frontend insertion attempt per successful result, not a new end-to-end delivery guarantee.
Deferred promises:
- Provider replacement, another audio service, continuous listening, and automatic submission are outside this increment. Reuse the current provider and configured access.
- Durable transcript history, recovery after closing/reloading the view, offline delivery, and a terminal delivery-acknowledgment protocol are not promised. These are delivery boundaries, not rules for rejecting otherwise supported ordinary terminal input.
- This story does not redesign session layout. Reconcile its control and feedback with SEED-199's compact header and mobile screen when that work lands; queue order is not a blocking dependency.
Key examples:
1. An open phone refinement terminal already contains `Review ` → activate the microphone before Mark as done, speak `the session header`, and Stop → the native input contains `Review the session header` once, has focus, and has not submitted. Edit it, then press Enter → the session receives the edited instruction. Typing during capture remains ordinary terminal input.
2. An attached desktop terminal with keyboard focus → Tab to the microphone, start, and stop → the same input behavior, with understandable state and reachable Close. Where Mark as done is unavailable, the microphone remains with the other session actions.
3. Provider text includes `Review the header\nthen the controls` → transcription completes → those words enter as one line without an Enter or control action. Launch dictation still uses its existing blank-line append and 4,000-character review behavior; terminal insertion does not inherit that launch-only limit or review dialog.
4. Missing configured access, refused permission, unsupported capture, empty speech, or failed transcription → activate dictation → the applicable safe recovery guidance is visible and announced; ordinary typing remains usable and another recording requires an explicit action. Reuse existing settings guidance rather than another credential store.
5. Session A has active recording, pending permission, or transcription → Close it, mark it done so the view closes, or open B → capture is released and the request is cancelled. Deliver an already-completed response late, or grant permission late → no text appears in B or a reopened A.
6. Session A's terminal disconnects before insertion → transcription completes → the complete transcript stays visible in A with an explanation and Discard; another recording waits for that result to be settled. Reconnect → no automatic insertion. Choose Insert → text enters A once and focus returns there; choose Discard instead → no text is sent. Close or switch to B before choosing → the retained text is discarded and never enters B. A transcript already handed to an open connection is never automatically replayed after reconnect, because delivery may already have happened.
