# Which retrospective findings deserve the next reader's attention?

Doughnut and Pygardon developers write findings, and project and Open Dough maintainers spend time matching, triaging and revisiting them. The two pilots ask different questions of the same execution history. Each can be judged against current practice in both projects.

### Pilot which new retrospective findings to record

**Identity:** SEED-401#pilot-new-retrospective-findings

**Goal.** Help the reviewer of a Doughnut or Pygardon execution decide which first observations deserve a project or Open Dough maintainer’s attention. A consequential first incident, a reusable practice or evidence bearing on an open question should reach the person who can use it. An uneventful review can finish with its ordinary execution proof. The pilot succeeds if that choice reduces the combined work of writing and triage while preserving the consequential reports.

**Scope**

- At an enabled process review, ask “What future decision could this observation change?” before allocating a new finding ID or assembling occurrence metadata. Name the choice beyond accepting this execution’s own proof, and the evidence that bears on it. A concrete effect, an identifiable path to harm, a technique with a credible use elsewhere, or evidence that narrows a live question can qualify on first sight. Cause, remedy, recurrence and measured cost can remain unknown.
- When the only evidence is a control doing its expected job, leave it with the execution proof. When a first report qualifies, use the ordinary recording and ownership rules. For an existing match, use current occurrence rules. The [repeat pilot](#pilot-repeat-retrospective-findings) owns proposed changes to them. ID recovery and evidence storage belong to [SEED-402](SEED-402-stable-client-finding-records.md).
- Compare current and candidate decisions on the same historical evidence, then assess a small, independently selected ordinary-work sample in **each** pilot project under the [shared comparison](#pilot-comparison). Look in execution evidence for what either reviewer missed, including runs with no entry. Charge the effort of checking omissions to the comparison. Keep the verdict scoped to the observed route and exposure. Release and adoption beyond the pilot are separate decisions.

**Choice to test.** Today the writer can record any supported one-off or practice. The log compares impact, recurrence, actionability and evidence quality under size pressure. Leaving that choice to triage protects breadth but pays for metadata and review even for entries later pruned. Moving those retention criteria earlier would let a writer weigh relative importance, at the cost of comparing a first observation with the backlog before knowing whether either needs attention. Trial the narrower decision question instead. It borrows exception reporting from operations, where routine readings stay in the operating record and an exception reaches someone who can investigate or change a decision. Here the execution proof is the record and the maintainer is the recipient. A successful practice or an observation that narrows uncertainty can also deserve attention, even when operations ran normally. [Recording rule](../../Distribution/src/skills/dough-execution-retrospective/references/process-finding-recording.md) · [Retention rule](../../Distribution/src/skills/dough-execution-retrospective/references/bounded-process-log.md)

**Decision.** Keep the candidate if consequential first reports survive, fewer routine entries reach triage and combined effort falls. Revise if it loses a serious one-off, a transferable practice or a supported question solely because the remedy or cost is unknown. The strongest risk is a quiet log that hides a missed incident and leaves the next reviewer to reconstruct it. Use the independent sample to check both losses and reconstruction effort. Missing exposure or incomparable effort leaves that part of effectiveness open.

### Pilot when a repeat adds useful retrospective evidence

**Outcome.** A maintainer can see when another incident changes priority, the explanation, or the assessment of a correction, without rereading an account of each harmless repeat. Today's recording rule requests a row for each new execution. The collector already matches aliases, distinguishes executions and shortens duplicate narrative after collecting it. Test the choice at the time of recording. [Client recording rule](../../Distribution/src/skills/dough-execution-retrospective/references/process-finding-recording.md) · [Existing collection and reconciliation](../../.agents/skills/collect-client-feedback/SKILL.md#collect-reconcile-and-adopt)

**Trial question.** What do we learn from this occurrence that could change the next action? Preserve a material new effect, cumulative cost that changes priority, a newly affected workflow, corrected attribution or an observation of the adopted response succeeding or failing. Where frequency drives the decision, retain a compact, recoverable count of distinct project/executions with representative locators. Make an identical reread a no-op. A new cause can deserve its own identity even when the symptom is familiar.

## Compare the pilots with current practice

For each pilot, state the comparison and keep/revise criteria before observing fresh runs. Use the same historical inputs for current and candidate wording, varying only the selected recording decision. Show the reviewer what was knowable at that execution. Reveal later corrections, retirements and rejected remedies only when judging the decisions. Historical replay is exploratory. Record the project, guidance revision and actual route used for each fresh observation. [ADR 0005](../../docs/adrs/0005-cross-tool-validation-accepted.md) · [ADR 0010](../../docs/adrs/0010-definition-of-improvement-accepted.md)

Select a small ordinary-work sample in **each** pilot project from story, Git or CI history before inspecting the findings files. Include executions that produced no report. Check for missed first incidents, accumulating costs and evidence for or against an earlier response. Count decisions changed, consequential misses and duplicate narratives reaching triage. Compare writer and downstream reviewer effort, including checking skipped cases, using available time, tool or token evidence. Keep active time, elapsed time and token counts distinct. Record sample counts, exposure and missing evidence. A shorter file or a higher fraction of graduated findings alone cannot establish a gain. Use existing execution records and each pilot's assessment to avoid maintaining a ledger of rejected observations. [Existing evaluation measures](../../docs/maintainer/empirical-process-control-research.md#a-small-set-of-decision-oriented-measures)
