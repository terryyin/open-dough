## Invocation and ownership

A request to run `maintain-feedback-cycle` names both maintenance phases and
ordinary publication, subject to narrower current instructions. Merely reading,
authoring or encountering a finding does not run either phase. The runbook keeps
its explicit `collect-client-feedback` shared-only invocation and its existing
former-runbook meaning. The wrapper owns composition only; the maintained local
skill owns classification/lifecycle/local selection, and the collector owns
reconciliation, retention/watch, shared priorities and cross-repository delivery.
No phase rule, Git reconciliation algorithm or persistent ledger is copied.

## Required context and target handoff

Representative selected alpha uses `master`, installed helpers under its own
`.agents/skills/`, canonical local `notes/ProjectFindings.md`, and shared
`DearDough.md`. The maintained source can live in Open Dough while alpha remains
the local phase's established project. The wrapper links the maintained source
and requires project-resolved helper compatibility before dependent writes. It
retains actual saved record locations and accepted candidate/target facts, and
resolves a current accepted checkout if a child retired its previous workspace.
A stale default checkout is not passed as post-local evidence.

Missing canonical evidence, inventory or installed helper is an affected-project
gap. Trace: wrapper **Establish the cycle and project set** -> source local
**Resolve the project and records** / **Select an owned checkout before writing**.
The affected dependent assessment/write/publication stops, saved records remain,
and supported projects proceed. The collector's maintained discovery and
retention/watch rules keep the incomplete scope explicit. This is a source
walkthrough; slice 2 owns a real unavailable-input observation.

## Consequential conflict walkthrough

Suppose alpha's configured target conflicts with the verified root/origin, or an
explicitly selected maintenance checkout also contains another session's private
commit. Trace: wrapper **Establish the cycle and project set** and **Complete the
local phase** -> collector **Resolve the maintained set and destinations**
(resolve conflicting paths/targets before writes) -> local delivery **Select an
owned checkout before writing** (whole result must be owned maintenance; an
explicitly selected checkout with unrelated work stops writes/publication).
The report cites the conflicting target or private suffix and asks for the exact
human target/ownership decision needed. No branch switch, blanket stash,
configuration rewrite or broadened publication resolves the conflict. Independent
supported projects remain eligible. No conflict was injected in the slice-1
native complete-input journey; slice 2 supplies unrelated-checkout proof.

## Useful outcome and evidence boundary

The complete-input native prompt supplies only invocation, inputs, conventions,
authority and isolation. It does not supply classifications, counts or priorities.
Fixture setup creates raw observations and real local origins but performs no
classification, story selection, adoption or maintenance publication. The native
agent must consume both maintained owners, perform each local pass before shared
use, preserve local stories under shared ordering and publish later shared edits.
Assess from actual canonical records, accepted origin history and native trace,
not its exit status or report alone. Runtime observation is Codex only. The thin
Claude pointer reuses the existing discovery mechanism; this conventional skill
change adds no installer/coexistence mechanism or native Cursor/Claude claim.

An accepted local SHA alone cannot establish the later shared result is accepted.
The wrapper explicitly carries that second delivery boundary and reports an
unfinished phase truthfully. Native observations and remaining gaps are recorded
