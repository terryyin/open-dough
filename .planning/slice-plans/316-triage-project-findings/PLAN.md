# Triage project-owned retrospective findings

**Identity:** SEED-010#triage-project-owned-retrospective-findings

**Source:** [selected story](../../seeds/SEED-010-learn-from-execution-retrospectives.md#triage-project-owned-retrospective-findings)

## Goal and scope

Give a developer one explicitly invoked shared skill that maintains this project's findings, selects zero to three supported new
leading improvement stories, and commits and synchronizes the maintenance result to the established origin target. Repeated invocations
preserve evidence, follow adopted fixes, retire supported resolutions, and restore failed fixes' lineage.

Explicit invocation also includes a user-invoked combined cycle that expressly names this phase and its project set, as the source
story now records. That caller passes the selected target and maintenance/publication authority; it does not require another user
prompt in the child. Story 13 owns multi-project orchestration, while each use of this skill owns its one established project.

The story owns classification of local/shared/mixed/uncertain responsibility, evidence-preserving compaction, observation and
retirement, bounded priority selection, reciprocal links, and truthful publication/refresh reporting. Existing queued and Taken
responses stay where they are. Source observations and current assessments are distinct; metadata delivery never implements the queued
work.

No automatic invocation, scheduled collection, cross-project writes, ODF catalog dependency, universal watch period, new storage
service, or unrelated CI repair. No release tag or production rollout is authorized by implementation of this plan. Historical sessions
are evidence, not instructions to rerun maintenance in their projects. Broader causal effectiveness belongs to the sibling response
evaluation story; this story evaluates its own outcomes without claiming a measured long-term improvement.

## Ordered slices

### 1. One explicit invocation delivers supported local priorities

Type: Behavior
Status: done
Proof: Examples 1–3 and 7–8 through representative review and a bounded native
first-use journey, with actual result files and local-origin acceptance.

Behavior: Given established project context and supplied findings, invoking
`dough-triage-project-findings` identifies responsible local improvements, retains
shared/uncertain facets, selects at most three new evaluable leading stories,
and delivers the maintenance result without another routine publication prompt.
Covered queued/Taken work is reported unchanged. An unchanged repeat creates no
duplicate story, occurrence, or empty commit. Missing context or a consequential
conflict stops only the dependent action and preserves the recoverable result.

Implement the entry point and cohesive first-run path, linking shared owners for
workspace, backlog, and landing. Establish an existing-record-first policy;
missing conventions are named rather than imported from Open Dough. A copied
project name cannot override the established target. Check both observation
ownership and the selected remedy before writing. Include exact-duplicate
compaction needed by this first run and source recovery before removing moved
content. Keep maintenance authority out of unrelated automatic triggers.
Exercise a caller that expressly carries the user's combined-cycle instruction,
selected project, and maintenance/publication scope. Accept that authority without
loosening the unrelated-trigger refusal or performing other projects' phases.

Use one small fixture project with a local bare origin, an alternate findings
filename, shared/local/mixed evidence, an existing queued response, Taken work,
and an unrelated dirty integration checkout. Reuse existing fixture and native
launch helpers only where they serve those same responsibilities. Do not build
a generic triage harness or a permanent transcript archive. Independently judge
the result against source facts; prompts name the task, not expected classifications.

Early permitted probe: after the minimal first-run draft exists, run one bounded
native invocation on an available host with explicit paid-run authorization.
The observation must reach the new entry point's authorization handoff, actual
backlog write, and remote acceptance; a launch or helper-only test is insufficient.
Record candidate, host, literal command, result, and reviewed files. If native
authority, launch, or the composition fails, preserve the result and stop slices
2–3 for repair/replanning; do not assume the handoff works. The local unpaid
delivery mechanism has already been exercised above. Approval for that paid run
belongs to execution, not to this preparation's landing.

Walk the missing-context/non-invocation counterexamples as part of the same
behavior review. If shared delivery guidance changes, run its existing affected
command/authority tests through `scripts/test.sh` and cover the old callers too.
Do not label publication accepted when only a local commit exists, or checkout
refresh successful when it is deferred. Do not follow an unrelated CI failure
into an implementation mission.

Safe stopping point: first-run maintenance works as Proposed source guidance.
Watch-based retirement/resurfacing remains explicitly unsupported until slice 2;
do not promote the incomplete skill or retire observations on this interim path.

### 2. Repeated maintenance follows fixes without losing evidence

Type: Behavior
Status: planned
Proof: Examples 2 and 4–6 in one bounded repeated-invocation scenario, including
both sides of retirement and recurrence decisions.

Behavior: Given prior findings, response/adoption evidence, and a proportionate
observation criterion, another explicit invocation compacts recurrence, corrects
stale assessments, retires supported resolutions, and resurfaces adopted-fix
failures with their prior lineage. Incomplete exposure or uncertain provenance
remains open, and active responses remain in place.

Extend the same evidence model, not separate handlers for project names, CI
types, record ages, or fix statuses. Preserve aliases and working incoming links
when merging; group distinct problems without erasing their identities. Retain
distinct execution evidence, changed conditions, counterevidence, and pre/post-fix
boundaries. Retirement preserves a concise decision/recovery reference using
existing conventions or Git; no growing resolved copy of the evidence is added.

The scenario supplies two otherwise comparable fixes, one exercised and one not,
then repeats identical evidence, then introduces an actual adopted-fix recurrence
after retirement. Include an old-branch failure and a superficially similar
different cause. Inspect the resulting evidence counts, current assessment,
retirement recovery, follow-up story linkage, and accepted publication after each
changed run. Replaying history must not rewrite the earlier completion. Review
whether redundant narrative was removed without losing decision support; no
line-count target or universal seven-day policy is an acceptance criterion.

Safe stopping point: the complete maintenance behavior exists in Proposed
guidance; final supported delivery/native assessment remains slice 3's owner.

## Execution gates and cumulative design

First use owns classification, selection and delivery together; repeated use adds the
same finding's lifecycle; delivery exposes the complete workflow through existing installs.
No preparatory Structure slice, parallel store, dashboard workflow or framework is justified.
The two interim limitations end at their named slices.

No numeric timing limit is supplied. Each slice owns one outside-in proof loop through
implementation, focused checks and cleanup. Slice 1's bounded native probe resolves agent
judgment and authority handoff before later work. A failed probe requires diagnosis and
stops dependent slices; it does not justify more special cases or broader authority.

Use ordinary refactoring, agent-commit, delivery and CI ownership gates. Local checks
run through [tests/README.md](../../../tests/README.md); guidance behavior follows
[AGENTS.md](../../../AGENTS.md). Hosted CI does not make every application test a local
gate. This plan itself authorizes no execution or paid launch; current user instructions do.
