The checkout-bound entrypoints `ci-mailbox.mjs`, `watch-ci.mjs`, and
`ci-host-hook.mjs` decide whether to run their CLI body by comparing
`import.meta.url` with `pathToFileURL(process.argv[1]).href`. On macOS, a
script invoked through `/tmp/...` may load from its canonical
`/private/tmp/...` location. Those two spellings name the same file but compare
unequal, so the process exits successfully without entering the requested CLI
behavior.

Goal: each of these three entrypoints recognizes an invocation whose module
path and argv path resolve to the same file, including the macOS `/tmp` to
`/private/tmp` case, while imported-module use remains side-effect free and an
unrelated script path is never treated as the entrypoint. The beneficiary is
an execution coordinator or host hook launching an installed checkout-bound
CLI through a symlink-equivalent path.

This is distinct from ODF-052. That finding recorded a probe receipt that was
printed but did not attach a Cursor hook; here the direct-entry guard prevents
the CLI body from running, so no receipt or hook processing can occur at all.

## Findings and scope

- The same literal URL comparison appears in all three entrypoints, so fixing
  only the observer launcher would leave mailbox commands or host-hook delivery
  vulnerable to the same path spelling difference.
- The correction owns the smallest shared direct-entry decision and focused
  process-level proof for these three scripts. Before adding a new helper,
  inspect the current product for an existing reusable direct-entry solution.
- Preserve each script's current CLI validation, output, lifecycle behavior,
  import exports, and error handling. Do not redesign the CI observer, mailbox,
  host adapters, checkout discovery, or hook registration.
- Recognize file identity only. Do not broaden the entry condition to basename
  matches, prefix matches, or arbitrary command equivalence, and do not make
  imports execute CLI behavior.
- Tests must use an actual symlink-equivalent path boundary rather than mocking
  the expected boolean, and must retain a negative import or unrelated-path
  observation.

## Ordered slices

### 1. Run checkout-bound CLIs through realpath-equivalent entry paths
Type: Behavior
Status: done

Behavior: When any of the three affected scripts is launched with an argv path
that is symlink-equivalent to the loaded module path, it enters its existing CLI
body and produces the same observable result as a canonical-path launch.
Importing the module continues to expose its API without running that body, and
an unrelated path remains ineligible.

Proof: Add focused process-level cases beside the affected CI runtime tests.
Create a disposable symlinked checkout or entry path, invoke each script through
the non-canonical spelling, and assert script-specific evidence beyond exit
status: a mailbox probe receipt for `ci-mailbox.mjs`, an emitted observer event
or controlled validation result for `watch-ci.mjs`, and parsed-input/output or
error behavior for `ci-host-hook.mjs`. Retain canonical invocation coverage and
negative import/unrelated-path coverage. Run the focused test files, then
`npm run lint` and `PATH=/opt/homebrew/bin:$PATH npm test`.

Delivered: extracted the shared decision into
`src/skills/dough-execute-plan/scripts/ci-direct-entry.mjs`
(`isDirectCliEntry(moduleUrl, argvPath)` — literal-URL fast path, falling back
to `fs.realpathSync` comparison, fail-closed on error), matching the existing
`realpathSync` idiom already used in `ci-mailbox-location.mjs` for a related
identity comparison (no new mechanism introduced). `ci-mailbox.mjs`,
`watch-ci.mjs`, and `ci-host-hook.mjs` now call it in place of the inline
literal comparison; no other behavior in those files changed. `install.sh`'s
`managed_files` manifest gained the new source path so the installed payload
carries the module the other three now import.
